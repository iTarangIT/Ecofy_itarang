# Conflicts and decisions register

The handoff rule is: **do not invent behaviour**. Where the authoritative files (BRD v1.4, OpenAPI v1.0.1, schema v1.4, seed v1.1, UAT v1.1) disagree or leave a gap, this register records what was built and why, so iTarang can confirm or change it. Every entry is additive or the least-surprising reading; none changes a frozen rule.

| # | Where | Conflict / gap | Built as |
|---|---|---|---|
| 1 | OpenAPI `InstallationUpdate.status` vs schema `install_status` | The API enum lacks `NOT_STARTED`, which the schema has and defaults to. | `POST /cases/{id}/installation` creates `NOT_STARTED`, or `SCHEDULED` when `scheduledOn` is given. `NOT_STARTED` is never set through PATCH. |
| 2 | OpenAPI `GET /audit` | Response typed as an array of arrays. | Returns a flat array of audit entries (`{id, at, actorId, actorName, actorRole, action, entityType, entityId, caseId, before, after, reason, ip}`). |
| 3 | OpenAPI `EpcPartner`, `Financier` | Read schemas have no `id`, but `PATCH /epc-partners/{partnerId}` needs one. | `id` is included in both list responses (additive). |
| 4 | OpenAPI `CaseCreate.fromEstimateId` | References a quick estimate that `POST /calculator/estimate` never stores and whose result has no id. | Accepted and ignored except that its presence sets `source = CALCULATOR`. The client saves the estimate as assessment v1 through `POST /cases/{id}/assessments` after creation. |
| 5 | OpenAPI `POST /webhooks/sms/delivery` | "Shared secret" mentioned, no scheme defined. | Requires header `X-Webhook-Secret` equal to env `SMS_WEBHOOK_SECRET`. Matches `sms_messages.provider_msg_id` and sets DELIVERED / FAILED. |
| 6 | OpenAPI untyped reads (activities, appointments, timeline, installation, asset, notifications, dashboards, audit, withdrawals, quotes list, offers list, file-of-case, payment-status, OTP status) | No response schema. | Shaped 1:1 from the schema tables in camelCase; a few additive read endpoints were added so the UI never guesses state: `GET /cases/{id}/quotes`, `GET /cases/{id}/offers`, `GET /cases/{id}/file`, `GET /cases/{id}/financing/decisions`, `GET /cases/{id}/installation`, `GET /cases/{id}/down-payment`, `GET /cases/{id}/payment-status`, `GET /cases/{id}/withdrawals`, `GET /cases/{id}/documents`, `GET /otp/{challengeId}`. |
| 7 | OpenAPI `If-Match` typed as integer | Not an RFC 7232 entity tag. | Kept as the integer case version, exactly as specified; `Case.version` is echoed in every case response. Quoted values (`"7"`) are also accepted. |
| 8 | OpenAPI `OtpChallenge` | No status / attempts fields, so the UI cannot show `LOCKED`. | `status` and `attemptsRemaining` added to `OtpChallenge` (additive). |
| 9 | Seed `gates.s4_order = PARALLEL` | Semantics undefined. | Both tracks open at once; S4 → S5 still requires eligibility **and** an ACTIVE unexpired quote with a composed offer. |
| 10 | OpenAPI `SessionRegister` is `{}` and the security scheme is an httpOnly cookie `sb-access-token` | A browser cannot set an httpOnly cookie after a client-side Supabase sign-in. | `POST /auth/session` accepts `{accessToken, refreshToken}` (additive), verifies the token and sets the httpOnly host-only cookies itself. Refresh happens server-side only. |
| 11 | BRD §6 rate limit "login 5/min/IP" | Sign-in happens client-side against Supabase per the OpenAPI flow. | Delegated to Supabase's own rate limiting; recorded here. Device-code and OTP limits are enforced by the platform. |
| 12 | BRD §6 idempotency list vs OpenAPI | BRD names four routes; OpenAPI also requires the key on `POST /cases` and `POST /cases/{id}/reacceptance`. | OpenAPI wins: six routes require `Idempotency-Key`. Same key + different body → 422 `IDEMPOTENCY_KEY_REUSED` (BRD says 422; the OpenAPI code name is used). |
| 13 | Seed `intake.consent_attestation_text` | The commit body must carry the attestation text. | The text sent must equal the configured setting (trimmed), otherwise 422 — so the logged confirmation is always the approved wording. |
| 14 | Schema `documents.sha256 NOT NULL` vs three-step upload | A row is needed before the PUT to reserve the key, but the digest is known only after. | The row is inserted with a sentinel digest of 64 zeros and is invisible until `POST /cases/{id}/documents` commits the real digest. |
| 15 | OpenAPI `FileRecord.acceptedTotalInr` visible to all roles | It is the quote total, not a financing value. | Visible to every role that sees the case (it is the customer's accepted price). Financing amounts remain in `*_values` tables. |
| 16 | BRD 4.2 "Not eligible" | No sub-status is named for S4 after a NOT_ELIGIBLE decision. | Sub-status `NOT_ELIGIBLE` (additive) so iTarang Admin sees the route-or-close prompt. |
| 17 | UAT-28 "S2 closes at once" vs schema `withdrawals.status` default REQUESTED | A withdrawal before acceptance has no confirmation step. | Withdrawals at S0–S4 are inserted as CONFIRMED and close the case immediately with `closure_reason = WITHDRAWN`. |
| 18 | PostgreSQL version | BRD: 16 on RDS. Development runs on the staging RDS (18.3); tests also ran on 17.6. | The handoff DDL runs unchanged on 15, 16, 17 and 18; the 26 schema checks pass. |
| 19 | Schema tests assume autocommit | Running the file inside one transaction keeps `SET LOCAL ROLE ecofy_app` alive across blocks and breaks T14. | `db/scripts/run-schema-tests.mjs` inserts `RESET ROLE` after every block and rolls the whole run back, so the checks run against any database without leaving data. The checked-in test file is verbatim. |
| 20 | Seed uses `\g /dev/null` | psql on Windows cannot open that path. | The seed wrapper rewrites it to `\g NUL` on win32 in a temporary copy. The checked-in seed is verbatim except for the staging toggle in #21. |
| 21 | Login on staging without email delivery | FR-01.3 requires an emailed device code; staging has no SES. | Setting `auth.device_verification_required` (default `true`) lets staging skip the device code. It must stay `true` in production. |
| 22 | OpenAPI `SystemsImport.documentId` | The standard systems template must be a committed document, but documents belong to a case. | V1: the template file is uploaded as an `OTHER` document on any case the admin can see, then referenced by id. A case-less upload endpoint is the cleaner follow-up. |
| 23 | Drizzle | The BRD says `drizzle-kit pull` then `drizzle-kit migrate`. | `pull` output is used for query typing only (hand-corrected for `citext`). Migrations are the SQL files under `db/schema/` applied by `db:apply-schema`; `generate` / `push` are never run (they would rewrite the authoritative DDL). |
| 24 | BRD §2 / Build Baseline S0.1 "Push to iTarang" vs the iTarang CRM (sandbox.itarang.com) | The BRD has iTarang work S1+ inside this workspace. iTarang also wants pushed leads to reach the Sales Head in its own CRM, which has its own code and database. | Additive sync, documented in `docs/ITARANG_CRM_SYNC.md`: Warm push / Hot → signed `lead.pushed` to the CRM, later stage changes → `lead.stage_changed`; the CRM posts `lead.accepted/assigned/activity/returned/closed` to `POST /integrations/itarang/events` (HMAC, not in the OpenAPI). Inbound events run the existing services as one iTarang Admin integration user, so gates, RLS and audit are unchanged. At S1 a CRM assignment assigns the case to that user (S1 → S2). The CRM does NOT name the person: iTarang decides internally who handles a lead, so the event and every signed call carry the fixed labels "iTarang team" / "iTarang CRM" (decided 25 Sep 2026). In addition, every `/api/v1` route accepts a signed service call (`X-Itarang-Signature` over method + path + body) acting as an ACTIVE iTarang Admin/Caller named in `X-Itarang-Act-As`. That is how the CRM does anything the iTarang Admin does in this workspace; the route's x-roles, RLS, gates and audit are unchanged, and the session/device checks do not apply to it. Tables in `db/schema/0001_itarang_crm_sync.sql`. Closed 25 Sep 2026: S2+ case work (calls, meetings, assessment, offer, OTP, installation, withdrawals) happens in the iTarang CRM through the §5 signed API (CRM E-307/E-308); Ecofy Admin work (eligibility, sanction, payout, asset) and iTarang-Admin masters/settings stay in this workspace. |
