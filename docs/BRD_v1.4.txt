# 1. Scope and principles
| In scope (V1) | Lead intake, qualification, queue, follow-up, EPC visits, assessment with a designable calculator, offer, SMS OTP acceptance and File, financing status and routing, installation and disbursement records, asset and EMI status, withdrawals, documents, dashboards, audit, admin portal settings. |
| Out of scope (V1) | KYC, underwriting and credit decisions; moving or collecting money; EMI calculation; EPC and financier logins; customer-facing app; WhatsApp or dialer integration; IoT telemetry; after-sales service. |
| Platform boundary | The platform records states and enforces gates with evidence. It never performs KYC, underwrites, calculates EMIs, or touches money. No PAN, bank statements or AA data are stored. |
| Overrides | The platform records permitted workflow and technical overrides and does not prevent them: choosing a system other than the recommended one, offering above the eligibility limit, starting installation before sanction. Each carries a reason or acknowledgement and an audit row (earned rule 4). Quote-price override is not supported in V1: the price is the EPC partner's quote. |
| Commercials | Billing is contractual and off-platform in V1. The platform shows usage counts (seats, Files, active assets) and never blocks access on a commercial threshold. |
| Decision source | Business answers are frozen in Build Baseline v1.2. Where a decision was not answered, it is a portal setting; open items are built as the baseline states. |

# 3. System design
# 3.2 Architecture decisions
| Decision | What | Why |
| Modular monolith, own process, own DB | One Next.js codebase with 18 modules behind service interfaces; PM2 processes ecofy-lms (web) and ecofy-worker (jobs); database ecofydb on the shared RDS instance. | Five users do not justify services. Clean module walls let us split later without rewrites. |
| State changes only through the case state engine | Every stage change goes through one service that checks gates, bumps the version, and writes history, audit and outbox rows in one transaction. | One place to test gates; no stage drift from ad-hoc updates. |
| Transactional outbox, then BullMQ | Events are rows in outbox_events, published by a relay to BullMQ; handlers are idempotent. | No lost or phantom notifications when a transaction rolls back. |
| Tenant and role in the database session | Each request transaction sets app.tenant_id, app.user_id and app.role; RLS enforces tenant isolation, worker scope and money visibility. | A bug in one API cannot leak another role's data. |
| Money in separate *_values tables | Eligible and sanctioned amounts live in eligibility_values and financing_values, readable only by the role named on the row. | Agreed rule 5 enforced by the database, not by UI hiding. |
| Immutable calculator releases | Calculator values, appliances and systems are versioned releases; Ecofy approves; assessments store release_id. | Any past recommendation can be reproduced and explained. |
| No free-form formula editor | Admin edits values, lists, rules and texts inside a fixed 9-step formula. | A wrong formula would silently mis-size every customer. |
| Supabase Auth, own project | Separate auth project for the Ecofy tenant; users and data stay in ecofydb. | User pools never mix with the iTarang CRM. |
| Presigned S3 uploads | Browser uploads straight to a private bucket; metadata committed after upload; 5-minute URLs. | Files never pass through the app server; nothing is public. |

# 4. Case state engine
# 4.2 Transitions and gates
A stage changes only through the state engine. Every call carries If-Match with the case version, checks the gate, and writes stage history, audit and an outbox event in one transaction. Failed gates return GATE_NOT_MET naming the missing condition.
| From | To | Trigger | Actor | Gate | API |
| S0 | S1 | Temperature set to Hot | EU / EA (platform moves it) | None: instant, automatic | POST /cases/{id}/temperature |
| S0 | S1 | Push to iTarang | EU / EA | Temperature is Warm | POST /cases/{id}/push |
| — | S1 | iTarang-sourced lead created | IA | Consent tick; owner = iTarang | POST /cases |
| S1 | S2 | Assign to caller | IA | Caller active | POST /cases/{id}/assign |
| S1 | S0 | Return to Ecofy | IA | Reason from list; goes to the qualifier | POST /cases/{id}/return |
| S2 | S3 | Advance to assessment | IC / IA | Completed meeting or EPC visit (setting, on) | POST /cases/{id}/advance |
| S3 | S4 | Confirm assessment | IC / IA | An assessment version exists | POST /assessments/{id}/confirm |
| S4 | S5 | Send offer (OTP sent) | IC | Eligible with Ecofy (or current financier) · one ACTIVE, unexpired quote · offer composed | POST /offers/{id}/otp |
| S5 | S6 | Customer OTP verified | Customer, via caller's screen | OTP matches within expiry and attempts; File created and locked | POST /otp/{id}/verify |
| S4 | Not eligible → next financier | IA | Reason recorded; eligibility requested from the next financier | POST /cases/{id}/route-financier |
| S6 | S6* | Lower sanction | EA | Sanctioned < accepted total → sub-status REACCEPTANCE_PENDING | POST /cases/{id}/financing/decisions |
| S6 | Rejected → next financier | IA | Rejection reason recorded | POST /cases/{id}/route-financier |
| S6* | S7 | Re-acceptance OTP verified | Customer, via caller's screen | Revised acceptance recorded on the same File | POST /otp/{id}/verify |
| S6 | S7 | Sanction recorded | EA (Ecofy) / IA (other) | No re-acceptance pending | POST /cases/{id}/financing/decisions |
| S7 | S8 | Disbursement recorded | EA (IA for other financiers) | Sanctioned · installation INSTALLED or COMMISSIONED · photos + customer acceptance letter | POST /cases/{id}/disbursement |
| Any open | CLOSED | Close / confirmed withdrawal | Stage owner; IA after S5 | Closure reason; withdrawal rules (M14) | POST /cases/{id}/close · /withdrawals |
| CLOSED | S0 | Reopen | Platform on re-upload / IA | Reason; history kept. Never for a case that reached a File: a new linked case is created instead (database trigger) | POST /cases/{id}/reopen |

4.3 Case stage and installation run in parallel. An installation record may be created and progress while the case is still at S6. The case enters S7 only when the sanction is recorded and no re-acceptance is pending. Installation status (SCHEDULED, IN_PROGRESS, INSTALLED, COMMISSIONED, STOPPED) and case stage are separate state machines until the S7 → S8 gate, which needs both: a sanction, and an installation at INSTALLED or COMMISSIONED with photos and the customer acceptance letter. Starting an installation while the case is at S6 without a sanction shows a warning and needs an acknowledgement, which is audited.
Sub-statuses: S4 ELIGIBILITY_PENDING · QUOTE_PENDING · OFFER_READY; S5 OTP_SENT; S6 AWAITING_DECISION · REACCEPTANCE_PENDING · REJECTED_ROUTING; S7 INSTALLING · INSTALLED; CLOSED carries closure_reason.

# 6. API structure
| Contract | ecofy_openapi_v1.0.1.yaml is the request and response contract for every endpoint; this catalogue is its summary. If they differ, the OpenAPI file wins. |
| Base path | https://ecofy.itarang.com/api/v1 · JSON · Next.js route handlers calling module services; modules never read each other's tables directly. |
| Auth | Supabase session in an httpOnly, host-only cookie. Middleware resolves the tenant from the host, loads the user and role, and opens a transaction with SET LOCAL app.tenant_id, app.user_id, app.role. |
| Responses | Success: { data, meta }. Error: { error: { code, message, details, requestId } }. |
| Error codes | VALIDATION_FAILED 422 · UNAUTHENTICATED 401 · SESSION_REPLACED 401 · DEVICE_VERIFICATION_REQUIRED 401 · FORBIDDEN 403 · NOT_FOUND 404 · VERSION_CONFLICT 409 · GATE_NOT_MET 409 (names the failed gate) · SEAT_LIMIT 409 · RATE_LIMITED 429. |
| Concurrency | Case-changing calls send If-Match: <case version>; a mismatch returns VERSION_CONFLICT. |
| Idempotency | Idempotency-Key header required on OTP send, import commit, quote upload commit and offer creation; stored in idempotency_keys; a replay returns the first result for 24 hours; the same key with a different body returns 422. |
| Pagination | Cursor based: ?cursor=&limit= (max 100); filters as query parameters. |
| Uploads | Three steps: POST .../upload-url → PUT to S3 → POST commit with checksum. |
| Money | Whole rupees as integers. Fields a role may not see are omitted, not sent as null. |
| Time | ISO-8601 in UTC; the UI shows IST. |
| Rate limits | Login 5 per minute per IP · OTP send 3 per offer per hour · OTP verify 5 attempts. |
| Versioning | /v1 now; breaking changes go to /v2. |

# 7. Database
| Engine | PostgreSQL 16 on the shared RDS instance (ap-south-1); database ecofydb; app role ecofy_app. |
| Keys | UUID primary keys (gen_random_uuid); identity bigints for append-only logs; case numbers ECF-1001 onwards. |
| Tenancy | tenant_id on every table except tenants itself, child tables included; RLS enabled on every table; policies read app.tenant_id, app.user_id and app.role set per transaction. The host lookup runs before a tenant is known, so it goes only through resolve_tenant(). Migrations and seeds run as the owner role; the app connects as ecofy_app, which cannot write tenants or tenant_domains. |

| History | Append-only tables (audit_log, activities, case_stage_history, seat_ledger, installation_events, file_acceptances): UPDATE and DELETE revoked from the app role. |
| Migrations | Drizzle schema generated from ecofy_schema_v1.4.sql (drizzle-kit pull), then drizzle-kit migrate in the pipeline. Expand-then-contract for breaking changes. |
| Functions | offer_within_limit(case, total) and resolve_tenant(host): SECURITY DEFINER, fixed search_path, return only what the caller may know. | Tested | ecofy_schema_tests_v1.4.sql: 26 self-checking tests that raise on failure, so CI stops. They cover RLS and tenant_id on every table, the host lookup, tenant isolation of child tables, caller scope and hidden amounts, the within-limit answer, Ecofy scope before and after routing, payout visibility, seat cap, audit immutability, appointment rules, KYC document types, File reopen, recommendation states, provisional quotes, trusted devices, standard-system and release rules, the consent confirmation, and the File lineage chain (case, version, total, verified OTP, no edits). # 9. Non-functional requirements
| Area | Requirement |
| Performance | Lists and case pages p95 under 500 ms; a 5,000-row import finishes within 2 minutes; OTP SMS sent within 5 seconds. |
| Availability | 99.5% monthly in working hours; planned deploys outside working hours. |
| Security | TLS everywhere; host-only cookies; tenant_id and RLS on every table (checked in CI by ecofy_schema_tests_v1.4.sql); private S3 with 5-minute URLs; secrets from Secrets Manager; OWASP top-10 checks before go-live. |
| Privacy (DPDP) | Consent stored per lead plus upload confirmation; recordings deleted after 60 days; import files and raw rows after 30 days; no KYC, PAN, bank or AA data; mobiles masked in lists. |
| Audit | Every change and export audited in the same transaction; audit_log insert-only; retained for the contract term. |
| Backups | Daily RDS snapshots; 7-day point-in-time recovery; restore tested before go-live and quarterly. |
| Scale | Sized for 5 staff users and tens of thousands of cases; no redesign needed up to 50 users. |
| Browsers | Latest Chrome, Edge and Safari; responsive down to a 13-inch laptop; caller screens usable on a tablet. |
| Observability | Structured JSON logs with requestId; PM2 log rotation; uptime check on /health every minute; error tracking with alerts to IA. |

## Pipeline (GitHub Actions)
| # | Stage | What happens |
| 1 | Pull request | Typecheck, lint, unit tests (state engine gates, calculator formula) and ecofy_schema_tests_v1.4.sql against a disposable PostgreSQL; the pipeline fails on any failed check. |
| 2 | Merge to main | Build with output: standalone; copy .next/static and public into the standalone folder. |
| 3 | Sandbox deploy | Run drizzle-kit migrate on ecofydb_sandbox; upload the release to /srv/ecofy/releases/<sha>; switch the current symlink; pm2 reload ecofy-lms ecofy-worker; smoke tests hit /health and log in with a test user. |
| 4 | Production release | Tag v*; manual approval; take an RDS snapshot; migrate (expand-only); deploy as in step 3; smoke tests; roll back automatically if /health fails. |
| 5 | Rollback | Point the symlink at the previous release and reload PM2. Migrations are forward-only (expand, then contract in a later release), so old code runs on the new schema. |

| Known trap on this stack / With output: ‘standalone’, PM2 must run node .next/standalone/server.js with .next/static and public copied in. Running next start under PM2 against a standalone build fails; this has broken deployments before. |
